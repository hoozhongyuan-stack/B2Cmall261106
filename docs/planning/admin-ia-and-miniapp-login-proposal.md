# 后台信息架构调整 + 小程序登录合规改造提案

> 范围：① PC 后台一级菜单重组（门店履约合并、装修与设置拆分）；② 小程序微信登录增加协议勾选与退出登录。
> 原则：不改变业务能力，只收敛入口与补齐合规；路由尽量兼容，避免已有外链/收藏失效。

## 一、PC 后台：一级菜单重组

### 1.1 现状问题

| 问题 | 现状 |
| --- | --- |
| 门店相关入口分散 | 「履约」放自提核销/同城配送，「门店」只放门店管理，总部要跨两个一级菜单操作同一家门店 |
| 「设置」过重 | 11 个二级项混在一起：店铺资料、支付、运费、装修、发布、日志、子账号……找东西全靠记忆 |
| 装修类无归属 | 首页运营位、素材库被塞进「设置」，与「配置」语义不符 |

当前一级菜单共 9 个：经营、商品、交易、客户、营销、履约、门店、设置（装修/素材在设置内）。

### 1.2 目标结构（推荐）

```
经营        数据概览 / 经营看板
商品        商品列表 / 分类管理 / 标签管理
交易        所有订单 / 批量发货 / 售后管理 / 评价管理
客户        客户列表 / 用户标签 / 等级规则 / 会员卡与储值 / 积分规则
营销        优惠券 / 满减与秒杀
门店履约    门店管理 / 自提核销 / 同城配送          ← 3 合 1
装修        首页运营位 / 素材库                    ← 从「设置」拆出
设置        店铺信息 / 小程序发布 / 集成配置 / 支付设置 /
            运费模板 / 物流公司 / 系统状态 / 子账号 / 操作日志
```

一级入口由 9 个降为 8 个，语义变为「经营 → 交易 → 履约 → 内容 → 系统」。

**拆分依据**

| 新分组 | 收纳内容 | 判断标准 |
| --- | --- | --- |
| 门店履约 | 门店管理、自提核销、同城配送 | 都围绕「某家门店的履约现场」，日常由门店/运营高频使用 |
| 装修 | 首页运营位、素材库 | 面向 C 端展示的内容编排，改动频率高、需要预览 |
| 设置 | 店铺信息、发布、集成、支付、运费、物流、系统、子账号、日志 | 低频、一次配好，偏系统与合规 |

> 运费模板与物流公司保留在「设置」：它们属于交易规则配置，不是视觉装修；若后续希望交易侧自助，可再迁到「交易 → 配送规则」。

### 1.3 交互与路由

- **默认落点**：点「门店履约」图标进入门店管理；点「装修」进入首页运营位。

## 二、小程序：登录页、协议勾选与退出登录

### 2.1 现状问题

- 当前是**全静默登录**：[client.ts](file:///Users/hoo/Documents/trae_projects/trae_B2C_1106/apps/miniapp/src/api/client.ts) 首次请求直接用 `code` 换 token，没有任何登录页与协议确认。
- 无用户协议/隐私政策入口，不满足微信审核与个人信息保护合规要求。
- 无退出登录入口，用户无法切换账号或停止使用。

### 2.2 目标体验

```
首次进入需要登录的页面
   └─ 未登录 → 登录页
         ├─ 展示：Logo / 一句话价值 / 【微信一键登录】
         ├─ 协议区：☐ 我已阅读并同意《用户协议》《隐私政策》
         ├─ 未勾选时按钮置灰；点协议打开全文页
         └─ 勾选后点击 → 微信授权 → 换取 token → 回到原页面
已登录 → 不再拦截（同版本协议下静默续期）
我的 → 底部「退出登录」→ 二次确认 → 清 token → 回首页未登录态
```

### 2.3 登录拦截策略

| 页面类型 | 示例 | 未登录行为 |
| --- | --- | --- |
| 公开浏览 | 首页、分类、搜索、商品详情、门店列表 | 不拦截，正常匿名浏览 |
| 需身份 | 购物车、结算、订单、售后、我的、地址、评价、优惠券、门店中心 | 跳登录页，登录后回跳原页面 |
| 静默续期 | token 过期/401 | 清 token 后走一次静默登录；若协议版本已升级则跳登录页重新确认 |

实现建议：`api()` 增加 `auth: 'required' | 'optional'`（默认 required），401 时不再无条件静默重登，而是抛出 `NEED_LOGIN` 由页面路由到登录页；顶部增加 `useLoginGate()` 处理回跳参数 `redirect`。

### 2.4 协议管理（合规留痕）

- **协议正文**：小程序新增静态页 `pages/agreement/index?type=terms|privacy`，正文由运营/法务提供；版本号统一定义在 `@shanye/shared` 的 `AGREEMENT_VERSIONS`，前后端共用。
- **首次登录必选**：`POST /auth/wechat-login` 增加 `agreed: true`、`agreementVersion`、`privacyVersion`；缺少或版本不匹配返回 400，不签发 token。
- **留痕表**（推荐，便于审计）：

```prisma
model UserConsent {
  id        String   @id @default(cuid())
  userId    String
  type      String   // USER_AGREEMENT | PRIVACY
  version   String
  agreedAt  DateTime @default(now())
  ip        String?
  userAgent String?
  user      User     @relation(fields: [userId], references: [id], onDelete: Cascade)

  @@unique([userId, type, version])
  @@index([userId])
}
```

- **版本升级**：登录响应返回 `agreementVersions`；本地缓存版本与最新不一致时，下次进入需身份页面弹出「协议更新确认」，确认后补记一条 consent。
- **微信侧隐私授权**：weapp 构建下同时接入 `Taro.requirePrivacyAuthorize`（或 `button open-type="agreePrivacyAuthorization"`），确保首次调用手机号/地址等隐私接口前完成微信官方隐私授权；H5 预览仅走自有勾选。

### 2.5 退出登录

- 「我的」页底部新增「退出登录」，`confirmAction` 二次确认，执行：清 `shanye_token` → 清本地用户缓存（地址/结算草稿可保留）→ `Taro.reLaunch` 到首页，未登录态。
- 服务端 JWT 无状态，无需接口即可退出；为审计可加 `POST /auth/logout`（记录时间），非必须。
- 退出后「我的」页展示「登录 / 注册」入口，点击回到登录页。

### 2.6 合规补充（建议同期做）

1. 隐私政策需列明收集项：微信 openid、手机号、收货地址、订单与支付记录、设备信息。
2. 提供「注销账号」入口（我的 → 设置 → 注销账号），7 天冷静期或即时匿名化按法务口径。
3. 协议页支持分享/复制链接，便于客服答疑。

### 2.7 受影响文件

- 小程序：新增 `pages/login/index`、`pages/agreement/index`；改造 `api/client.ts`（鉴权模式、`NEED_LOGIN`）、`mine/index.tsx`（登录/退出入口）、`app.config.ts`。
- 后端：`auth/user-auth.controller.ts`（登录入参校验、consent 写入、版本返回）、`schema.prisma` + 迁移、`openapi.yaml`。
- 测试：`auth` 契约测试（未勾选 400、勾选成功、版本不符 400、consent 落库）、E2E（首次登录勾选、拒绝勾选不可登录、退出后需重新登录）。

### 2.8 验收标准

1. 清空缓存首次进入「我的」→ 登录页；未勾选时按钮不可点。
2. 勾选并登录成功，数据库存在两条 consent 记录（terms/privacy 各一条，含版本）。
3. 协议版本升级后，再次登录必须重新确认，确认前拿不到 token。
4. 「我的 → 退出登录」后回到首页未登录态，再次进入需登录页。
5. 公开页面（首页/商品/门店）未登录仍可浏览。
6. 微信开发者工具中首次触发隐私接口时出现官方隐私弹窗，同意后可正常使用。

## 三、实施顺序建议

| 阶段 | 内容 | 说明 |
| --- | --- | --- |
| 第 1 步 | 后台菜单重组（只改 `MENU`/图标/面包屑） | 纯前端、低风险，可独立上线 |

| 第 3 步 | 协议版本升级提示、注销账号、微信官方隐私授权完善 | 合规加分项 |
| 可选 | 后台路由语义化迁移（/stores、/decoration） | 有外链成本，建议单独评估 |
