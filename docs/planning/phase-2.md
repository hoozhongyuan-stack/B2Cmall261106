# 山野商城二期规划

状态：已按确认方向更新
前置：一期已完成并部署联调环境（car.aition.art）；真实微信支付已完成代码接入，尚待真机完成一笔真实支付验收。

已确认方向：
- 二期重心：**上线保障与运营效率 + 会员复购**
- 图片存储：**本地磁盘 + 备份 + 磁盘告警**（二期不迁 OSS）
- 物流：**批量发货 + 物流公司字典 + 单号展示**（不接第三方轨迹查询）
- P1 增长能力：**满减活动 + 限时秒杀（均二期）、付费会员卡 + 储值卡（均二期）、评价晒图 + 买家秀**
- 会员折扣规则：**等级折扣与付费会员折扣取最优（不叠加）**

## 1. 一期回顾

### 已完成
- 交易闭环：商品/分类/规格/库存 → 购物车 → 结算（会员折扣 + 优惠券 + 运费）→ 下单（幂等 + 库存预占）→ 支付 → 发货 → 收货 → 售后/退款 → 评价。
- 增长能力：优惠券、会员等级、积分、客户管理、评价审核与商家回复。
- 后台：24+ 页面，商品/订单/售后/营销/客户/店铺/子账号/操作日志/数据概览/集成配置/小程序发布。
- 小程序：21 个页面，商品多图轮播与详情图、素材库本地图片、微信支付 JSAPI、售后与评价。
- 工程：共享金额与状态机、OpenAPI 契约测试（38 条）、Playwright E2E、CI 门禁、独立测试库、一键部署、限流与错误上报。
- 集成：AppID/AppSecret、微信支付商户参数与密钥、订阅消息模板配置位、小程序构建上传与体验版二维码。

### 一期遗留 / 技术债（二期必须收口）
| 项 | 现状 | 影响 |
|---|---|---|
| 真实微信支付真机验收 | 代码与签名链路已验证，未完成真实扣款 | 无法确认支付闭环 |
| 订阅消息 | 仅后台配置模板 ID，无发送实现 | 发货/售后结果无法触达用户，PRD P0 缺口 |
| 首页运营位 | 首页仅分类 + 固定推荐，无轮播/金刚区配置 | 无法做活动与内容运营 |
| 批量发货 | 仅支持单笔发货 | 订单一多，履约效率低 |
| 退款结果 | 以同步响应为准，无回调/主动查询 | PROCESSING 需人工确认，存在对账风险 |
| 图片存储 | 本地磁盘，部署不删除但备份只含数据库 | 磁盘故障会丢失商品图 |
| 可观测性 | 结构化日志 + 客户端错误上报，无外部告警 | 线上故障发现依赖人工 |
| 评价晒图 | 用户评价无图片上传入口 | 内容与转化弱于同类商城 |
| 客服 | 仅客服电话 | 无在线咨询入口 |

## 2. 二期目标

1. **可上线**：真实支付、消息触达、退款对账、监控告警达标，完成真机与弱网回归。
2. **可运营**：首页与内容可配置，履约效率提升，售后结果自动触达。
3. **可复购**：在会员等级与积分之上，补齐付费会员/储值权益，形成锁定与复购。
4. **可增长**：用满减/秒杀与评价晒图提升转化与客单。

不做大而全：二期仍坚持「一个商家把货卖好、把服务做好」的主线，多商家、直播、分销等规模化能力放三期。

## 5. 关键技术方案

### 5.1 订阅消息（Outbox 模式）
- 新增 `NotificationLog`：模板、用户、场景、请求体、微信返回、状态、重试次数。
- 新增 `SubscriptionGrant`：记录用户授权（templateId、scene、授权时间、可用次数）。
- 业务事务内只写 outbox，异步任务发送，避免外部调用拖慢下单/发货。
- 失败重试 + 去重键（业务单号 + 模板 + 场景）。
- 小程序在支付成功、售后提交、发货等节点引导订阅授权。

### 5.2 首页运营位
- 新增 `HomeBanner`、`HomeNav`、`HomeSection`（推荐拆表，便于查询与审计）。
- 点击动作枚举：`product` / `category` / `search` / `page`，后台选择目标并校验存在性。
- `/api/home` 聚合返回运营位；后台支持启用/排序/定时上下线与预览。
- 图片统一走素材库，禁止外链。

### 5.3 履约
- `ExpressCompany` 字典表（编码、名称、排序、启用）。
- 批量发货接口：入参为订单 + 物流公司 + 单号列表，逐单事务，返回成功/失败明细；失败不阻断其他订单。
- 单号展示与复制，不接第三方轨迹查询；物流详情页保留手工节点。

### 5.4 退款对账
- `Refund` 增加 `channelStatus`、`lastQueriedAt`、`notifyStatus`。
- 定时任务扫描 `PROCESSING` 退款，调用微信退款查询接口，更新状态并通知用户。
- 退款异常（ABNORMAL）进入后台待处理列表。

### 5.5 会员与储值
- `MemberCardPlan`（卡方案）、`MemberCard`（用户持有）、`MemberBenefit`（权益快照）。
- `StoredValueAccount`（余额）、`StoredValueLedger`（充值/消费/退款流水）、`RechargePlan`（充值套餐）。
- 余额支付作为独立支付方式接入订单支付；失败/取消原路退回余额。
- **会员折扣取最优**：同时持有等级折扣与付费会员折扣时，取应付金额更低的一档，不叠加。
- 资金类操作全部走事务 + 流水，后台提供台账与导出；储值按单用途预付卡口径落实退款、开票与资金存管要求。

### 5.6 营销计算
- 在 `packages/shared` 固化两条价格链路：
  - **普通商品**：原价 → 会员折扣（等级折扣与付费卡折扣**取最优、不叠加**）→ 优惠券 → 满减（按券后商品金额判断门槛）→ 运费。
  - **秒杀商品**：秒杀价 → 运费；**不参与**会员折扣、优惠券、满减。
- 会员折扣与满减/券的关系：先算会员折扣，再算券，再判断满减门槛，避免重复优惠。
- 活动模型：`Promotion`（满减/秒杀）、`PromotionScope`、`SeckillSku`（活动库存、限购）。
- 秒杀库存独立于 SKU 库存，下单时同时占用活动库存与普通库存，超时/取消释放。
- 所有金额规则必须有单测与契约测试覆盖。

### 5.7 图片与存储（二期保持本地）
- 维持 `UPLOAD_DIR/assets` 本地存储，不迁 OSS；保留 `StorageProvider` 扩展位，便于三期迁移。
- 上传目录纳入备份脚本；磁盘使用率告警；恢复演练写入上线检查清单。
- 评价晒图沿用素材校验（类型/大小/魔数），增加用户级频率限制与审核状态。

### 5.8 可观测性
- 沿用 `x-request-id` 与结构化日志，接入错误追踪（Sentry 或云监控）。
- 告警项：5xx 比例、支付回调失败、退款异常、磁盘使用率、备份失败、任务堆积。
- 关键业务埋点：下单成功率、支付成功率、发货时长、退款时长、消息触达率、会员转化。

## 8. 风险与依赖

- **订阅消息授权限制**：微信一次性订阅每次授权只能发送一条，需要在关键节点反复引导，不能承诺 100% 触达。
- **储值合规**：储值卡二期落地，必须在开发前完成单用途预付卡合规评估，明确退款、开票、资金存管与余额有效期口径，并写入活动规则与用户协议。
- **资金风险**：余额支付、会员卡退款需要完整流水与对账，避免负余额与重复退款。
- **秒杀并发**：活动库存与普通库存需隔离，防止超卖与普通订单占用秒杀库存。
- **本地存储单点**：通过备份、磁盘告警与恢复演练降低风险；三期再评估 OSS/CDN。
- **单人开发**：严格按 A → B → C → D 推进，每批不超过 2 个能力域，避免同时开战线。
- **合规**：评价晒图、营销活动文案需审核；秒杀/抽奖类玩法需评估微信规则。

## 9. 已确认结论

- 二期重心：上线保障与运营效率 + 会员复购
- 图片：本地 + 备份 + 磁盘告警，不迁 OSS
- 物流：批量发货 + 物流公司 + 单号展示，不接轨迹查询
- 营销：满减活动与限时秒杀**均二期**，先满减、后秒杀
- 会员：付费会员卡与储值卡**均二期**
- 会员折扣：等级折扣与付费会员折扣**取最优，不叠加**
- 价格链路：普通商品走「会员折扣（取最优）→ 优惠券 → 满减」；秒杀商品仅用秒杀价，不叠加其他优惠
