# 山野商城三期规划

状态：已按确认方向起草，待评审
前置：二期迭代 A–D 已完成本地开发与验收；真实微信支付真机验收、储值合规评估仍待收口，不阻塞三期功能开发。

已确认方向：
- 三期主线：**履约与到店**（同城配送、到店自提、核销、门店履约）
- 门店形态：**轻量多门店**（门店级库存、订单归属、门店看板与对账；不做分账与商家入驻）
- 基础设施：**全文搜索**（仅此一项；OSS/CDN、批量导入导出、在线客服/工单不进入三期）
- 延续二期的取舍：单商家自营、本地图片存储 + 备份、不接第三方即时配送、不做拖拽建站

## 2. 三期目标

1. **可到店**：用户可选择到店自提或同城配送，门店能接单、核销、送达，形成完整的本地履约闭环。
2. **可多店**：一个商家下多个门店，门店有独立可售库存与订单归属；总部可看全局，门店只看本店，支持门店日结与对账。
3. **可找货**：商品搜索支持中文关键词、拼音首字母、分类/价格/标签筛选与多维排序，替代当前仅按标题 `contains` 的匹配。
4. **可度量**：门店履约时效、自提核销率、配送超时、门店库存预警进入经营看板。

仍坚持「一个商家把货卖好、把服务做好」：不做多商家平台、不做平台分账。

交付：
- `Store`、`StoreSku`、`StoreStockLog` 数据模型与迁移

- 库存来源规则：快递 → 总部仓；自提/配送 → 门店库存

验收：
- 门店可创建并配置营业时间、自提与配送能力
- 门店库存独立扣减与回滚，50 并发抢 10 件成功恰为 10、无负库存

- 门店看板数字与订单明细一致

### 迭代 B：到店自提与核销
交付：
- 结算页选择自提门店与自提时段，免收货地址（保留手机号）
- 订单金额：自提运费为 0，复用 `freightCents`
- 支付成功后生成核销码（防猜测、唯一、可失效）
- 核销台：扫码/输码、待核销列表、核销记录

- 取消、退款、超时关单后核销码失效

验收：
- 支付后立即出码，核销员可在 3 秒内完成核销
- 重复核销、跨门店核销、已退款订单核销均被拒绝且幂等
- 核销记录可追溯到操作人、时间、方式
- 自提订单不产生收货地址与快递单号

### 迭代 C：同城配送

- 超时未送达可在看板识别并提醒

## 5. 关键技术方案

### 5.1 门店与权限
- `Store`：编码、名称、电话、区域、详细地址、经纬度（可选，仅展示）、营业时间 JSON、自提开关、配送开关、配送费与免配送门槛、配送时段 JSON、公告、状态、排序。
- 新增 `AdminStore`（管理员与门店多对多）：一个门店账号可管理多个门店；总部账号不建关联，默认全部门店可见。
- 新增 `AdminRole.STORE` 为门店账号；后台顶部提供门店切换器，仅展示已授权门店。
- 权限矩阵：
  - 总部（SUPER/OPS/CS/WMS）：全局订单、商品、营销、财务、门店配置。
  - 门店（STORE）：授权门店的订单查看、核销、库存调整、看板与对账；不可改价、不可建活动、不可看未授权门店。
- 数据范围在 service 层强制过滤，不依赖前端隐藏；操作日志记录 `storeId`。

### 5.2 门店库存（双轨隔离）
- 总部仓库存继续使用 `Sku.stock / reserved`，仅服务快递订单，保持现状。
- 新增 `StoreSku`：`storeId + skuId` 唯一，含 `stock / reserved / safetyStock / status`；自提与配送订单只扣门店库存。
- 下单条件更新防超卖，与二期秒杀一致：
  ```ts
  const reserved = await tx.storeSku.updateMany({
    where: { storeId, skuId, status: 'ON_SALE', stock: { gte: quantity }, reserved: { lte: stock - quantity } },
    data: { reserved: { increment: quantity } },
  });
  if (reserved.count !== 1) throw new ConflictException('门店库存不足，请切换门店或改为快递');
  ```
- 取消、超时关单、退款按订单来源仓回滚；门店库存不足时前端引导切换门店或快递。
- 门店库存不由总部库存自动同步；调拨、盘点放 P1，避免三期一次引入过多库存概念。

### 5.3 履约方式与订单状态
- `Order.fulfillmentType`：`EXPRESS`（默认，兼容历史订单）、`DELIVERY`、`PICKUP`。
- 复用现有主状态机，不新增主状态，新增动作：
  - `pickup_verify`：`PAID → COMPLETED`（自提核销）
  - `accept_delivery`：`PAID → SHIPPED`（商家接单/配送中）
  - `deliver_complete`：`SHIPPED → COMPLETED`（已送达）
- 前端文案按履约方式渲染：`PAID` 显示「待发货 / 待自提 / 待接单」，`SHIPPED` 显示「待收货 / 配送中」。
- 状态机新增动作必须补单测，禁止在业务代码里手写状态判断（延续工程契约 R4）。
- `Shipment` 仅用于快递；自提使用 `PickupVerification`，配送使用 `Delivery`。

### 5.4 自提与核销
- 结算：选择门店 + 自提时段，校验门店 `pickupEnabled`、营业时间与时段容量；不需要收货地址。
- 核销码：支付成功后生成 8 位随机数字码并落唯一索引，同时声明 `pickupCodeExpiresAt`；二维码内容只含订单号与签名，不暴露用户信息。
- 核销校验顺序：门店匹配 → 订单状态为 `PAID` → 未退款 → 码未过期 → 未核销；重复核销返回「已核销」而非报错。
- 核销记录：`PickupVerification`（订单唯一、方式、操作人、时间、备注），与操作日志双写。
- 退款规则：未核销可原路退款并释放门店库存；已核销进入售后审核，不允许直接核销码退款。
- 超时：自提完成天数按门店配置（默认 7 天）。到期前 1 天触发订阅消息提醒；到期未核销自动完成订单（不自动退款、不回滚库存），售后时效从自动完成时间起算。自动完成任务记录操作日志，可在后台查看。

### 5.5 同城配送
- 配送范围：门店维护区县白名单（`StoreDeliveryRegion`），按收货地址 `region` 匹配；三期不做地图半径与实时距离，避免引入地图服务与坐标质量风险。
- 配送费：门店固定配送费 + 满额免配送费；结果写入订单 `freightCents`，结算页标注「配送费」。
- 配送时段：门店配置每日可选时段、截单时间与每时段最大单量；下单时校验时段是否已截单、是否超量。
- 配送单 `Delivery`：订单唯一、门店、状态（`PENDING / ACCEPTED / DELIVERED / CANCELLED`）、配送员姓名与电话、接单时间、送达时间、备注。
- 配送中退款：不做直接退款，提示用户拒收或送达后走售后，避免货物与资金脱节（P1 再补拒收流程）。
- 不接第三方运力；`DeliveryProvider` 预留接口，四期再评估。

### 5.6 全文搜索
- PostgreSQL `pg_trgm` 扩展 + `Product.searchText` + GIN 索引：
  ```prisma
  model Product {
    /// 标题 + 副标题 + 标签 + 分类 + 拼音首字母，写入时生成
    searchText String @default("")
    @@index([searchText(ops: raw("gin_trgm_ops"))], type: Gin)
  }
  ```
  如 Prisma 版本对操作符类支持受限，则在迁移中用原生 SQL 创建 GIN 索引。
- 召回：`searchText % keyword` 走 trigram；1 个字符的关键词降级为 `ILIKE 'keyword%'`；排序用 `similarity(searchText, keyword)` + `soldCount` + `sort`。
- 拼音：商品保存时用 `pinyin-pro` 生成全拼与首字母写入 `searchText`；新增回填脚本与 CI 校验（保存商品必更新）。
- 接口：扩展现有 `GET /api/products`，新增 `priceMinCents / priceMaxCents / tagId / storeId / sort=new`；P1 增加搜索词统计接口，热词由搜索日志聚合生成，不做人工维护。
- 抽象 `SearchProvider`，当前实现为 PostgreSQL，保留后续替换 Meilisearch/Typesense 的扩展位；三期不引入额外中间件。

### 5.7 金额与运费
- `calculateOrderAmount` 不新增优惠概念，只扩展运费入参来源：
  - 快递：沿用现有满额包邮 + 区域例外。
  - 自提：`freightCents = 0`。
  - 配送：门店固定配送费 / 满额免配送费。
- 会员包邮权益对自提无意义，对配送是否生效需在门店规则中明确（建议：会员包邮仅作用于快递，配送按门店规则）。
- 优惠券、满减、秒杀规则不变；秒杀 + 自提/配送的组合沿用现有分摊逻辑，需补组合单测。

### 5.8 通知与看板
- 复用二期订阅消息能力，新增模板位：自提待取、核销成功、配送接单、配送送达；模板 ID 仍在「集成配置」维护。
- 门店看板指标：今日订单、营业额、退款、待核销、待配送、库存预警、平均接单时长、平均送达时长。
- 门店对账：按日/按月汇总订单数、商品实收、运费、退款、核销数、配送单数，导出 CSV；不拆分资金流水。
- 总部看板增加门店维度筛选与门店排行。

### 5.9 数据迁移与灰度
- 迁移只增不毁：新增门店相关表与订单可空字段，历史订单默认 `EXPRESS`、`storeId = null`。
- 上线顺序：先门店与库存（只读校验）→ 自提（单店灰度）→ 配送（单店灰度）→ 搜索（全量）。
- 搜索索引上线前完成回填与容量评估，保留回滚到 `ILIKE` 的开关。

## 8. 风险与依赖

- **库存双轨复杂度**：总部仓与门店库存并存，容易出现扣错仓、回滚漏项。对策：以 `fulfillmentType` 唯一决定库存来源，回滚按订单行来源执行，并用契约测试覆盖取消、超时、退款、部分退款。
- **门店权限越权**：新增角色与数据范围过滤，必须在 service 层强制校验，不能只靠前端；建议单独一组门店越权契约测试。
- **核销安全**：核销码需随机、唯一、可失效，核销接口限流并记录操作人；禁止按订单号直接核销。
- **自提自动完成**：到期自动完成不可逆，需在下单页、订单详情与提醒消息中明确告知；后台保留 `AUTO` 记录与操作日志。
- **配送范围实现方式**：区县白名单简单可控，但与真实距离不一致；若业务要求按公里计费，需要地图服务与地址坐标，建议四期再评估。
- **搜索中文召回**：trigram 对单字与短词效果有限，需准备降级与同义词表；GIN 索引会增大存储与写入成本，需在上线前压测。
- **单人开发节奏**：严格按 A → B → C → D 推进，每批不超过 2 个能力域；门店与库存未稳定前不启动配送。
- **合规**：自提自动完成、配送拒收、门店发票口径需在开发前明确；储值合规仍是二期遗留前置项。

## 9. 已确认结论

### 方向
- 三期主线：履约与到店
- 门店形态：轻量多门店（门店库存、订单归属、门店看板与对账，不做分账）
- 基础设施：全文搜索进入三期；OSS/CDN、批量工具、客服/工单不进入三期
- 履约方式：快递、同城配送、到店自提三种并存，快递主链路不变
- 资金：仍由主商户号收款，门店只做经营归属与对账，不做门店独立收款
- 即时配送：不接第三方运力，商家自配送
- 配送范围：区县白名单，不做地图半径与实时距离

### 本轮确认规则
- 自提超时：按门店配置 N 天（默认 7 天），到期前提醒，到期**自动完成订单**，不自动退款
- 配送时段：按门店设置每日时段、截单时间与每时段最大单量
- 会员包邮：仅作用于快递，同城配送不享受；自提运费为 0
- 门店账号：一个账号可管理多个门店（`AdminStore` 多对多）
- 搜索热词：只做搜索日志统计与自动聚合，不做人工维护
