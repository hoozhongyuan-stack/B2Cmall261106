Technical Design · v1.0

把规则变成表、接口和状态机。

本方案覆盖 B2C 商城的中后台与小程序：数据模型、订单与售后状态流转、金额与库存的落地方式、模拟支付的替换点、权限与验收标准。四条已冻结决策（单商家自营、模拟支付、满额包邮、无积分抵扣）在表结构和接口里被显式体现。

范围 小程序 + 管理后台 + API 架构 单体 API + 单库 PG 金额 整数分 交付 M0–M4

01目标与约束

先说清楚哪些是硬约束——它们决定了哪些东西「不用建」。

已冻结决策技术后果
单商家自营不需要 merchant、settlement、分账与商家结算；所有表天然属于同一店铺，不引入 tenant_id 隔离
先用模拟支付支付能力抽成 PaymentProvider 接口；首版实现 MockProvider，回调契约与真实微信支付一致，后续换实现不改订单代码
满额包邮不建「首件/续件」运费模板表：shop_config 存门槛与固定运费，shipping_region_exception 存地区例外
订单不支持积分抵扣order 只有 5 项金额快照；points_ledger 只记发放与扣回，结算接口不接收积分参数

质量目标（可验收）

  • 下单、支付、退款三条链路具备幂等：重复请求不产生第二笔订单、第二次扣库存、第二次退款。
  • 并发下不超卖：库存扣减在数据库事务内完成，压测 200 并发抢 10 件库存，成功数必须恒为 10。
  • 订单金额可复算：任意订单的 5 项金额与优惠券记录能还原出应付金额，误差为 0（整数分）。
  • 状态非法迁移在服务端拒绝，前端仅做展示，不作为校验依据。
  • 后台所有写操作可追溯：操作人、对象、变更前后值。

02技术栈

选型标准是「一个人能维护、两端能共用类型、不为未来假设买单」。

层选型理由与取舍
小程序Taro 4 + React 18 + TypeScript一套代码可编译微信小程序与 H5 预览；与后台共用 TS 类型与状态机，避免两端规则漂移
管理后台React 18 + Vite + TypeScript与小程序同语言栈；设计稿是自建组件，不引入重型 UI 库，只用 tokens + 20 个左右基础组件
服务端NestJS 10 + Prisma模块划分天然对应业务域；守卫做角色鉴权；Prisma 事务与行锁足够覆盖库存与支付场景
数据库PostgreSQL 14订单、库存、退款需要强事务与唯一约束；用 pg_trgm 做商品搜索，首版不引 ES
缓存/锁Redis 7（可选启用）仅用于限流与订阅消息队列；库存不依赖 Redis，避免缓存与库不一致
对象存储S3 兼容（本地 MinIO / 云 OSS）商品图与售后凭证统一走预签名直传，服务端只存 key
部署Docker Compose：Nginx + API + PG + Redis + MinIO单机可跑，后续水平扩展只需把 API 无状态化
包管理pnpm workspace（monorepo）共享 packages/shared 的类型、金额工具、状态机
明确不引入：微服务、消息中间件、Elasticsearch、GraphQL、多租户框架。当前规模下它们只增加故障面，不增加能力。

03系统架构

两个前端、一个 API、一个库。所有业务规则只在一处实现。

分层职责

层职责不允许做的事
Controller参数校验、取当前用户、调用 Service、返回统一响应写业务规则、直接查库
Service业务规则、事务边界、状态机调用、发领域事件拼装视图数据、处理 HTTP 细节
Repository查询与写入，封装 Prisma出现业务判断（如「库存够不够」）
packages/shared金额计算、状态迁移表、DTO 类型、常量依赖任何运行时框架（须能同时跑在 Node 与小程序）

06金额与库存

这两块是最容易出错、也最该被写成单一实现的地方。

金额计算：单一函数，前后端共用

packages/shared/money.ts
// 全部使用整数分；顺序固定：商品 → 会员折扣 → 优惠券 → + 运费
export function calculateOrderAmount(input: {
  items: { priceCents: number; quantity: number }[];
  memberDiscountRate: number;   // 1 | 0.98 | 0.95
  coupon?: { thresholdCents: number; faceValueCents: number };
  freight: { freeThresholdCents: number; flatCents: number; isExceptionRegion: boolean };
}) {
  const goodsCents = input.items.reduce((s, i) => s + i.priceCents * i.quantity, 0);
  const memberDiscountCents = goodsCents - Math.round(goodsCents * input.memberDiscountRate);

  const afterMember = goodsCents - memberDiscountCents;
  const couponCents = input.coupon && afterMember >= input.coupon.thresholdCents
    ? Math.min(input.coupon.faceValueCents, afterMember) : 0;

  const afterCoupon = afterMember - couponCents;
  const freightCents = input.freight.isExceptionRegion
    ? input.freight.flatCents
    : (afterCoupon >= input.freight.freeThresholdCents ? 0 : input.freight.flatCents);

  return {
    goodsCents, memberDiscountCents, couponCents, freightCents,
    payableCents: afterCoupon + freightCents,   // 下限恒为运费
  };
}
规则实现要点
金额快照order 的 5 个金额字段在创建时一次写入，后续不随商品改价变化；退款只改 refunded_amount
券门槛判断用「会员折扣后金额」比较，不用原始商品金额；门槛不满足时前端置灰并说明差多少
运费判定先判断是否命中地区例外（例外优先），再判断是否达到包邮门槛
金额下限应付金额不允许小于运费；券最多抵扣到 0 元商品部分
退款金额上限为 order_item.subtotal - 已退金额；整单退时含运费退，部分退时不退运费

库存：预占而非直接扣减

order.service.ts · 创建订单（事务内）
await prisma.$transaction(async (tx) => {
  // 1) 行锁读取 SKU，天然串行化同一商品的并发下单
  const skus = await tx.$queryRaw`
    SELECT id, stock, reserved, price_cents FROM sku
    WHERE id = ANY(${ids}) ORDER BY id FOR UPDATE`;

  // 2) 可售 = stock - reserved；不足即回滚
  for (const line of lines) if (avail(line.skuId) < line.qty) throw new StockNotEnoughError();

  // 3) 预占库存，订单进入 PENDING_PAYMENT
  await tx.sku.updateMany({ where: { id: { in: ids } }, data: { reserved: { increment: qty } } });
  return tx.order.create({ data: { ...amount, status: 'PENDING_PAYMENT' } });
});
时点对 stock / reserved 的操作触发者
创建订单reserved += qty下单接口
支付成功stock -= qty，reserved -= qty支付回调
超时 / 主动取消reserved -= qty定时任务 / 取消接口
退款（未发货）stock += qty（可二次销售时）售后审核通过
超时释放：定时任务每 60 秒扫一遍 PENDING_PAYMENT 且超时的订单，用 version 乐观锁防止与「用户刚支付」并发冲突；释放库存与关单在同一事务内完成。

packages/shared/orderState.ts
export const ORDER_TRANSITIONS = {
  PENDING_PAYMENT: { pay_success: 'PAID', cancel: 'CLOSED' },
  PAID:            { ship: 'SHIPPED', refund_apply: 'REFUNDING' },
  SHIPPED:         { confirm: 'COMPLETED', refund_apply: 'REFUNDING' },
  COMPLETED:       { refund_apply: 'REFUNDING' },
  REFUNDING:       { refund_success: 'REFUNDED', refund_reject: 'PREVIOUS' },
  CLOSED:          {}, REFUNDED: {},
} as const;

export function can(action, from) { return Boolean(ORDER_TRANSITIONS[from]?.[action]); }
并发控制：所有迁移走 UPDATE order SET status=$next, version=version+1 WHERE id=$id AND version=$expected AND status=$from；受影响行数为 0 时返回 409，由前端提示「订单状态已变化，请刷新」。这是防止客服与买家同时操作导致状态错乱的唯一可靠方式。

  refund(input: { orderNo: string; refundNo: string; amountCents: number }): Promise<RefundResult>;
}

// 首版注册 MockProvider：createPayment 直接返回 { mock: true }，
// 前端点击「确认支付」后调用 /orders/:id/pay/mock-confirm 触发同一套回调处理
// 后续接真实渠道只需新增 WechatProvider 并改一行注册，订单与售后代码零改动
契约点要求
支付结果以回调为准前端跳转成功页不代表已支付；只有回调写入 payment.status = SUCCESS 后订单才迁移
回调幂等transaction_id 唯一索引；重复通知返回 200 但不重复处理
金额校验回调金额必须与 order.payable_amount 相等，否则记录异常并告警，不迁移状态
退款退款单号 refundNo 唯一；失败可重试，重试沿用同一单号
超时关单关单前再查一次支付状态，避免「刚支付成功就被关单」
替换真实支付时唯一要改的地方：部署配置里的 provider 注册与商户参数。订单表、退款表、状态机均不需要变更——这是首版就抽接口的唯一目的。

10权限与安全

四个内部角色的权限落到接口层级，不做到字段级配置。

角色可访问接口域硬限制
SUPER 超管全部不可删除自己；账号变更需二次确认
OPS 商品运营商品、分类、标签、库存、优惠券、积分与等级规则、素材不可看客户手机号全量、不可发货、不可退款
CS 客服订单查看、售后审核、评价管理、客户信息（脱敏）不可改价、不可改库存、不可发货
WMS 仓储待发货订单、发货、确认收到退货只见收货信息，不见支付金额明细

安全基线

  • 手机号在列表页一律脱敏（138****6621）；查看完整号码需单独权限并写入操作日志。
  • 后台登录：bcrypt 存储密码，连续 5 次失败锁定 15 分钟，登录与敏感操作记录 IP 与 UA。
  • 用户 token 与后台 token 使用不同签名密钥与过期时间，互不通用。
  • 上传走预签名，服务端校验 MIME 与大小（图片 ≤ 5MB），不信任客户端文件名。
  • 所有列表接口强制分页，pageSize ≤ 50；导出接口单独限流。
  • 富文本与商品详情做白名单过滤，防止脚本注入。

12测试与验收

先测规则，再测页面。金额与状态机的单测是这次开发的门槛。

必须存在的自动化用例

用例断言
金额组合矩阵会员折扣 × 券门槛边界 × 包邮边界 × 地区例外，至少 12 组；应付金额与手工计算完全一致
券边界券后金额为 0、券面额大于券后金额、门槛差 1 分，三种情况的行为符合规则
库存并发200 并发下单 10 件商品，成功订单恰为 10，库存不为负
支付幂等同一 transaction_id 回调 5 次，订单只迁移一次，库存只扣一次
超时关单支付与关单并发时，只有一个结果生效，且库存与状态一致
售后额度两次部分退款累计不超过实付；第二次申请被拒
非法迁移对 CLOSED 订单执行 ship，返回 409 而非 500

上线验收清单

  • 主链路：浏览 → 加购 → 下单 → 模拟支付 → 后台发货 → 确认收货 → 评价，一次走通且金额与页面一致。
  • 逆向链路：仅退款、退货退款、拒绝、超时关单，四类都能在后台看到完整轨迹。
  • 权限：4 个角色分别登录，看不到越权菜单与按钮，直接调接口返回 403。
  • 金额快照：改商品价格后，历史订单金额不变。
  • 视觉：按设计规范 v1.2 逐屏核对 41 屏，状态稿（空/错/载/禁）齐备。

13实施顺序

每个阶段都有明确的退出条件，不满足不进入下一阶段。

M0
骨架与契约
monorepo 初始化、packages/shared 的金额与状态机、Prisma schema 与迁移、统一响应与错误码、登录鉴权、种子数据（6 个商品 + 1 个店铺配置）。
退出条件：金额矩阵单测全绿；两角色可登录；Swagger 可访问。
M1
正向主链路
首页、分类、搜索、商品详情、购物车、结算、下单、模拟支付、订单列表与详情；后台商品列表与订单发货。
退出条件：一次完整下单到发货走通；并发抢购不超卖；订单金额与页面一致。
M2
售后与逆向
售后申请、列表、详情；后台审核、拒绝、确认收货、退款；超时关单定时任务；物流详情。
退出条件：四种逆向路径全部有记录；重复回调不重复退款；退款金额不超实付。
M3
营销与会员
优惠券领取与核销、新建券；会员等级与折扣；积分发放与流水（仅记录）；客户列表与详情；评价管理。
退出条件：券门槛与叠加规则按 PRD 生效；等级折扣参与金额计算且顺序正确。
M4
打磨与上线准备
41 屏视觉对齐、状态稿补齐、操作日志、导出、备份脚本、错误监控、真机联调。
退出条件：验收清单全过；弱网与空数据下无白屏。
