Engineering Contract · v1.0

能被 CI 拦住的才叫契约。

本契约只写两类内容：会直接造成返工或事故的规则，以及每条规则的检查点。全文两页以内，随代码一起演进；无法自动检查的条款不写进来。

适用 apps/api · miniapp · admin 生效 M0 起 变更 PR + 声明

01执行原则

三条原则决定这份文档的形态，也决定它不会变成废纸。

  • 少而硬。只保留会引发返工、资损或安全事故的条款。风格问题交给 Prettier/ESLint，不进契约。
  • 每条都有检查点。要么 CI 拦截，要么评审清单强制勾选；纯口头约定不写。
  • 文档随代码走。契约变更与代码变更在同一个 PR 内完成，不允许「先改代码后补文档」。
判断方法：如果一条规则无法回答「违反了会怎样被拦住」，就删掉它。这比多写十条更有价值。

02六条硬规则

每条都附检查点。CI 列为自动化，评审列为 PR 模板勾选项。

R1事实来源与冲突优先级
业务规则以 PRD 为准，实现方式以技术方案为准，视觉以设计规范为准。冲突时按 PRD > 技术方案 > 设计规范 > 代码 处理，代码不是事实来源。
评审：PR 模板声明文档：变更记录
R2接口契约单点定义
接口以仓库根目录 openapi.yaml 为唯一来源。前端类型与请求方法由 codegen 生成，禁止手写重复 DTO；破坏性变更必须新增版本号，不允许悄悄改字段语义。
CI：契约测试CI：codegen 后 diff 为空评审
R3数据契约
金额一律整数分，字段以 _cents 结尾；时间一律 timestamptz，接口输出 ISO 8601；迁移只增不毁（加字段 → 回填 → 弃用），禁止在同一次发布中删列或改类型。
CI：迁移 lint评审：schema diff
R4规则单一实现
金额计算与订单/售后状态机只允许存在于 packages/shared。Controller、页面、组件中不得复制判断逻辑（例如自己写「满 99 包邮」）。
CI：覆盖率门槛 90%CI：禁止跨层 import
R5视觉只认 token
颜色、字号、间距只能引用 packages/tokens。源码中禁止出现裸色值（#E2231A）与魔法字号（font-size:13px）。新增组件必须先在组件清单登记。
CI：ESLint 规则评审：组件清单
R6完成定义（DoD）
一张卡只有满足五项才算完成：四态覆盖、契约测试、可观测日志、无遗留 TODO、契约同步。未达标的卡不进验收。
评审：PR 模板五项勾选CI：TODO 扫描

03优先级与变更

冲突时按固定顺序裁决，变更走固定路径，避免「谁声音大听谁的」。

层级文档改动需要
1 业务规则PRD v0.2产品确认 + 变更记录（影响金额/状态必须重跑用例）
2 实现方案技术方案 v1.0技术评审；涉及接口需同步 openapi.yaml
3 视觉语言设计规范 v1.2设计确认；涉及 token 需同步 packages/tokens
4 代码实现仓库不得单方面改变以上三层

变更路径

  • 小改动（字段说明、文案、组件内部实现）：直接进 PR，在 PR 模板勾选「契约变更：是」并写一句影响范围。
  • 大改动（金额口径、状态机、接口破坏性变更、权限矩阵）：先写一页 RFC 落到 docs/rfc/，评审通过后再改代码。
  • 紧急修复：允许先合并后补文档，但必须在 24 小时内补 PR，否则 CI 阻断下一次合并。

04完成定义 DoD

五项全勾才算完成，少一项就是「看起来做完了」。

  • 四态覆盖。空、错、载、禁四种状态都有实现，不只是理想态；空态有出口按钮，错误态写清下一步。
  • 契约测试。新增或修改的接口，响应结构能被 openapi.yaml 校验通过；金额与状态相关逻辑有单测。
  • 可观测。请求带 requestId，关键写操作日志含订单号/商品 id/操作人，异常有明确错误码。
  • 无遗留。不提交 TODO、FIXME、被注释掉的代码块；临时开关必须写清理条件。
  • 契约同步。涉及接口、表结构、token 的改动，同一 PR 内更新对应文档。
验收口径：看勾选，不看口头说明。评审人只需检查这五项与 CI 结果，不重复判断风格问题。

契约测试（节选）

apps/api/test/contract/order.spec.ts
import request from 'supertest';
import { OpenApiResponseValidator } from 'openapi-response-validator';
import spec from '../../../../openapi.yaml';

const validator = new OpenApiResponseValidator({
  responses: spec.paths['/orders'].post.responses,
  components: spec.components,
});

it('POST /orders 必须返回契约字段', async () => {
  const res = await request(app.getHttpServer())
    .post('/api/orders').set('Idempotency-Key', 'k-001')
    .send({ addressId: 'addr_1024', items: [{ skuId: 'sku_1001', quantity: 1 }] })
    .expect(201);

  const errors = validator.validateResponse(201, res.body);
  if (errors) throw new Error(JSON.stringify(errors));

  expect(res.body.amount.payableCents).toBe(
    res.body.amount.goodsCents - res.body.amount.memberDiscountCents
    - res.body.amount.couponCents + res.body.amount.freightCents
  );
});

06明确不做

划清边界，避免契约膨胀成治理体系。

  • 不规定缩进、引号、命名大小写——交给 Prettier 与既有 ESLint 预设。
  • 不做字段级权限配置——四个角色足够，权限写在接口守卫里。
  • 不画架构图——技术方案已有，重复维护必然过期。
  • 不写运维手册——上线前单独成文，避免混在工程契约里。
  • 不设提交信息模板的强制校验——Conventional Commits 作为建议，不作为门禁。
