Product Requirements Document

B2C 商城：微信小程序商城 + 管理后台

本文档基于对参考站点（销客多 SaaS 商城后台）的功能拆解，定义一套单商家自营 B2C 商城的产品边界、交易主流程、功能需求与共享业务规则，供产品、设计、研发对齐决策。

版本 v0.2 状态 待评审 日期 2026-11-06 形态 微信小程序 + Web 管理后台 范围 核心交易闭环 + 营销会员

0摘要

一页看懂这次要做什么、不做什么。

产品形态
微信小程序商城
消费者浏览、加购、下单、支付、售后、评价的主阵地。
产品形态
Web 管理后台
商家做商品、订单、会员、营销与数据运营。
核心闭环
商品 → 下单 → 支付 → 发货 → 收货 → 售后
首版必须端到端跑通，且每一步都有异常回退路径。
差异重点
营销与会员
优惠券、等级会员与积分记录，构成复购抓手。
一句话产品定义 面向单个品牌/商家自营的微信小程序商城：消费者在微信内完成「挑商品 → 下单 → 支付 → 收收货」；商家在后台完成「上架 → 接单 → 发货 → 售后 → 复购运营」。

首版必须达成的可观察结果

  • 消费者能在小程序内完成一笔真实可追踪的订单，并在订单详情看到状态变化与物流信息。
  • 商家能在后台看到该订单、完成发货，发货后消费者侧状态同步为「待收货」。
  • 未支付订单在超时后自动关闭，库存正确释放，不需要人工干预。
  • 消费者能对已完成订单发起一次售后申请，商家能审核并完成退款，订单与库存同步回滚。
  • 优惠券与运费在同一笔订单中按统一规则计算，金额可复算、无二义。

1.3 调研结论与产品取舍

参考站面向「多商家 SaaS + 全渠道代运营」，功能覆盖极广。直接照搬会带来三类成本：大量用不到的后台配置项、跨模块耦合的规则（如同城配送/自提/核销）、以及需要额外资质与运营投入的能力（直播、微信小店、分销）。

保留（构成交易闭环，不可省）

  • 商品、分类、规格、库存、上下架
  • 购物车、下单、支付、订单状态流转
  • 快递发货、物流单号、确认收货
  • 退款/退货售后、评价
  • 客户列表、优惠券、积分、等级会员
  • 数据概览（今日/近 7 日核心指标）
  • 子账号与操作日志（最小可用）

收敛（首版不做，保留扩展位）

  • 同城配送、上门自提、核销员体系
  • 付费会员卡、储值卡、钱包提现
  • 拼团、秒杀、分销、活码、直播、微信小店
  • 公众号图文群发、自定义菜单运营
  • 多门店、多商家入驻、多级对账
  • 批量导入、库存同步、参数模板等效率工具
取舍原则 首版只解决「一个商家把货卖出去、把钱收回来、把售后处理掉」这一条主线。任何不参与这条主线的配置项，默认不进入 v1，避免把复杂度提前引入产品。

3核心流程与状态

流程与状态是本文档的「事实来源」，所有功能模块只引用，不重定义。

3.1 消费端主旅程

进入小程序→ 首页 / 分类 / 搜索→ 商品详情→ 选规格→ 加购 / 立即购买→ 确认订单→ 支付→ 待发货→ 待收货→ 确认收货→ 评价 / 售后

进入方式：微信会话卡片、扫码、搜索、小程序历史列表。首版不做公众号菜单跳转与广告投放承接。

关键分支

  • 未登录：可浏览商品；点「加购/购买/我的」时触发微信授权登录，登录后回到原页面并保留加购意图。
  • 库存不足：商品详情规格置灰并提示；结算页再次校验，失败则定位到具体商品行。
  • 未支付：订单创建后 15 分钟内可支付，超时自动关闭并释放库存。
  • 支付失败/取消：订单保持待付款，可从订单列表继续支付；不重复生成订单。
  • 收货后发现问题：已完成订单在售后期内（默认 7 天）可发起售后。

3.2 后台履约旅程

新订单提醒→ 订单列表筛选待发货→ 核对订单与备注→ 填写物流并发货→ 消费者确认收货→ 订单完成→ 售后退款
  • 发货时校验：订单必须为「待发货」，且每行商品数量已备货。
  • 发货后订单不可撤销；如需拦截，走售后「退款」流程，并在备注中标注。
  • 售后审核时限默认 48 小时，超时未处理在后台显示超时标记（不自动同意）。

MP-05 商品详情 · 关键规则

  • 库存展示：可售库存 ≤ 10 时展示「仅剩 N 件」；= 0 时规格置灰、按钮改为「已售罄」并禁用加购。
  • 价格展示：统一展示「到手价」规则见 5.1；划线价为商品原价，仅在高于到手价时展示。
  • 规格未选完：点击加购/购买时打开规格面板，不直接下单。
  • 商品失效（下架/删除）：详情页展示「商品已下架」，并推荐同类商品；购物车内该行标记失效且不可勾选。

MP-07 购物车 · 关键规则

  • 加购同一 SKU 累加数量，上限为该 SKU 可售库存与单品限购数（默认不限购）。
  • 勾选态与数量按用户持久化；进入结算只带入已勾选且有效的商品行。
  • 「去结算」校验：至少 1 行勾选、所有勾选行库存充足；任一失败则定位并提示具体商品。
  • 失效商品单独成区，支持「一键清空失效」，不参与金额计算。

MP-08 确认订单 · 关键规则

  • 进入页面即锁定一次价格与优惠试算结果；若在支付前商品价格或库存变化，提交时二次校验，变化则阻断并提示重新确认。
  • 地址为空时，结算页顶部提示「请选择收货地址」，提交按钮置灰。
  • 优惠券默认自动选中「最优可用券」，可手动切换或选择不使用；不可用券展示不可用原因。
  • 金额明细必须逐项展示：商品金额、优惠券抵扣、运费、应付金额，合计必须等于各项运算结果，不允许四舍五入误差（统一保留 2 位小数，见 5.1）。订单不支持积分抵扣。
  • 备注选填，上限 200 字。

MP-12 售后 · 关键规则

  • 可申请条件：订单为「待发货 / 待收货 / 已完成」，且在售后期内（确认收货后 7 天）；同一订单同时只允许一张进行中售后单。
  • 申请时必须选择售后类型（仅退款 / 退货退款）与原因（后台可配置），退款金额默认整单可退金额，不可超过实付金额。
  • 退货退款必须上传至少 1 张凭证图（≤ 5 张）；仅退款凭证选填。
  • 商家拒绝后，消费者可查看拒绝理由并撤销后重新提交，或联系客服。

AD-03 商品管理 · 关键规则

  • 商品结构：商品（SPU）下挂 1~N 个规格组合（SKU）；单规格商品默认生成 1 个默认 SKU。
  • 必填项：名称、分类、主图（≥1）、售价、库存；划线价、副图、详情图文为选填。
  • SKU 唯一：同一商品下规格值组合不可重复；编码（SKU Code）全局唯一，可自动生成。
  • 上下架：下架后小程序端不可见，已加购的行标记失效；出售中商品编辑价格立即生效（已生成订单不受影响）。
  • 删除：仅允许删除从未产生订单的商品；已产生订单的商品只允许下架，保证历史订单可追溯。
  • 库存：商家手动修改库存时，需记录变更前后值；不允许改为负数。

AD-05 订单管理 · 关键规则

  • 筛选维度：订单状态、支付状态、下单时间、商品名称、收货人/手机号、订单号。
  • 发货：仅「待发货」可操作；需选择物流公司并填写单号，支持批量发货（同物流公司）。发货成功后消费者端立即变为「待收货」。
  • 改地址：仅在「待发货」且未发货时允许，修改后需记录变更前后地址与操作人。
  • 订单备注：商家备注与消费者备注分开展示，商家备注仅后台可见。
  • 关闭订单：仅「待付款」可手动关闭，需填写关闭原因。
  • 导出：按当前筛选条件导出订单明细，字段包含订单号、商品、数量、实付、状态、收货信息、时间。

AD-06 售后管理 · 关键规则

  • 审核动作三选一：同意、同意退货、拒绝；拒绝必须填写理由。
  • 「同意退货」后等待消费者寄回；商家确认收货后方可发起退款，退款金额不得超过售后单申请金额。
  • 退款为原路退回，金额不可编辑；退款成功后回滚库存（仅整单退款，或售后单标记「商品可二次销售」）。
  • 售后单超过 48 小时未处理，列表标记「超时」，并在数据概览计入待办。

AD-09 优惠券 · 关键规则

  • 类型：满减券（满 X 减 Y）、无门槛券（减 Y）。首版不做折扣券与品类券。
  • 发放方式：后台手动发放给指定客户 / 全部客户；小程序首页与个人中心可领取。
  • 限制：每张券可设置每人限领张数（默认 1）、发放总量、有效期（固定区间或领取后 N 天）。
  • 状态：未使用、已使用、已过期、已作废；订单取消或整单退款时，已使用券在有效期内自动退回为「未使用」。
  • 叠加：一笔订单只能使用 1 张优惠券，不可与满减活动叠加（首版不做满减活动）。

5共享规则

这些规则被多个模块引用，必须全局唯一，不允许各页面自行解释。

5.1 价格与优惠计算

金额计算按固定顺序执行，任何页面展示的「应付金额」都由此顺序得出：

商品金额（Σ 售价 × 数量）→ 会员折扣→ 优惠券抵扣→ + 运费（满额包邮）→ 应付金额
  1. 币种与精度：人民币，所有金额以「分」为最小单位参与运算，展示时保留 2 位小数。
  2. 会员折扣：仅对商品金额打折，不作用于运费；折扣后金额向下取整到分。等级折扣与优惠券可同享。
  3. 优惠券门槛：按「商品金额 - 会员折扣」判断是否满足门槛，不含运费；抵扣金额不超过该小计。
  4. 积分：订单不支持积分抵扣，也不展示积分抵扣项；积分仅按后台规则发放并记录流水，不影响金额。
  5. 运费：按满额包邮规则计算——商品实付小计（扣除会员折扣与优惠券后）达到包邮门槛则免运费，否则按模板收取固定运费；运费不参与折扣与优惠券抵扣。
  6. 应付金额下限：优惠后应付金额小于 0.01 元时按 0.01 元计，保证支付渠道可受理。
  7. 一致性：下单、支付、退款、售后各环节均以订单创建时保存的金额快照为准，商品后续改价不影响历史订单。
为什么要快照 订单必须保存「商品金额、会员折扣、券抵扣、运费、应付」五项明细及所用的券。否则售后退款时无法复算，也无法解释给用户。

5.2 库存

  • 可售库存 = 实物库存 − 已下单未支付的预占库存。小程序端展示可售库存。
  • 预占：提交订单时锁定，支付成功转为实扣；订单取消/超时关闭时释放。
  • 并发：同一 SKU 在库存不足时下单必须失败并提示，不允许超卖；库存扣减需保证原子性（实现层负责）。
  • 退款回滚：整单退款或售后单标记「商品可二次销售」时回滚库存；商品已损毁则选择不回滚。
  • 售罄：可售库存为 0 时商品不下架，仅标记售罄，保留页面与收藏入口。

5.3 支付与退款

  • 支付方式：首版使用模拟支付，不接真实微信支付；支付流程、回调与状态流转按真实渠道设计，便于后续替换。真实商户号与小程序的接入延后。[TBD 接入时间]
  • 支付结果：以支付渠道异步回调为唯一可信结果；前端轮询仅用于展示，不作为入账依据。
  • 重复支付：同一订单收到多次成功回调时，后续回调只记录不重复入账，并对多付金额发起自动退款。
  • 超时：下单后 15 分钟未支付自动关单；关单后不可再支付。
  • 退款：原路退回，1~3 个工作日到账（以渠道为准）；退款失败时售后单保留「退款失败」标记，允许重试。
  • 资金口径：财务统计以「实付金额 − 已退款金额」为净收入；运费计入收入，优惠券抵扣计入营销成本。
